# Этап 2 — три дешёвых прототипа на 40 исходных видео

Дата: 2026-10-17. Новые веса не загружались; только существующие локальные кэши,
NumPy и OpenCV. Ни кадры, ни видео не экспортировались. Production scorer не заменён.

## Что проверено

1. **Стойкий остаток на столе между визитами**: census 3×3 (8 сравнений с соседями),
   пиксель изменён при расстоянии Хэмминга > 3/8; остаток присутствует минимум в 3
   последних кадрах из максимум 4. Признак — доля таких пикселей в общей видимой маске.
   Цель проверки — `cash_left_on_desk`, а не утверждение, что остаток является деньгами.
2. **Структурное изменение сейфа**: среднее `1 − ZNCC` по окнам 7×7 в видимой
   маске, затем медиана по последним кадрам. Проверяем `safe_left_open`.
   Окна с почти нулевой дисперсией дают нулевое изменение, чтобы не делить на ноль.
3. **Мелкий стойкий остаток сейфа**: крупнейшая компонента census-остатка,
   площадь ≥ 4 пикселей, стороны ≤ 0.3 роста кассира, заполнение ≥ 0.35;
   площадь нормирована на квадрат роста. Проверяем гипотезу `safe_key_left`.
   Это НЕ локализация замка или распознавание ключа.

Зоны, визиты, опорный и конечные кадры берутся из существующего candidates.py,
без ручных координат кабинета и без аннотаций в извлечении признаков. Применена
общая маска людей всех сравниваемых кадров: эрозия 5×5 для census
(blur радиуса 1 + сосед радиуса 1), отдельно 7×7 для ZNCC. Границы за
пределами кадра считаются невидимыми. Для каждого признака нужно минимум
50 допустимых центров и 3 конечных кадра; недостаток центров ZNCC не
подавляет доступный census. Кэш читается стандартным `load_video` в масштабе 0.5;
это существенное ограничение для ключа в несколько пикселей. Отсутствующий признак
не заменяется нулём. Разметка посетителей остаётся обучающим источником текущего
трекера; интервалы из visitors_train не подмешиваются как oracle в признаки.

Это три измеримых варианта двух практичных направлений отчёта 06 (устойчивость
к освещению и стойкость остатка), а не прототипы DINO/action recognition. DINO не
проверялся; частота пересчёта денег, отсутствие документа, возврат денег, смешение
купюр и помещение содержимого сумки в сейф здесь НЕ распознаются. Без нового
семантического сигнала подмена этих действий движением кисти была бы некорректна.

## Результаты

LOCO: 7 кабинетов, 40 уникальных development-видео, 21 положительное / 19 нормальных.
Х-47/48 исключены как дубли. Использованы confirmed VLM и одинаковые baseline
кандидаты/пороги выбора; новые признаки добавлены отдельно и совместно.

| Модель | CV accuracy | CV TP / FP / FN | Fit accuracy | Fit TP / FP / FN |
|---|---:|---:|---:|---:|
| baseline | 0.725 | 10 / 0 / 11 | 0.825 | 14 / 0 / 7 |
| proto_safe_zncc | 0.700 | 10 / 1 / 11 | 0.825 | 14 / 0 / 7 |
| proto_desk_persistent | 0.700 | 11 / 2 / 10 | 0.825 | 16 / 2 / 5 |
| proto_safe_small | 0.725 | 10 / 0 / 11 | 0.825 | 14 / 0 / 7 |
| combined | 0.675 | 11 / 3 / 10 | 0.825 | 16 / 2 / 5 |

**Все три отвергнуты для production.** Стойкий стол не разделяет позитивы и
негативы: 2 позитивных и 3 негативных кандидата, stump `separable=false`.
ZNCC разделяет имеющиеся train-кандидаты (1 позитив / 2 негатива), однако
добавляет FP на другом кабинете. Мелкий остаток не имеет положительного кандидата
Х-22 в допустимом окне ±8 с; stump вообще не обучен. Равенство CV в таком случае
не является доказательством полезности. Все три хранятся только как opt-in
исследовательские признаки, исключены из обычного train_scorer.

- proto_safe_zncc: CV FP на Х-14.
- proto_desk_persistent: CV FP на Х-19, Х-39.
- combined: CV FP на Х-14, Х-19, Х-39.

Полный проход извлечения кэша на Linux: 6.05 с / 40 видео,
включая декодирование JPEG и восстановление сцен, без CLIP-инференса. Это не
замер Mac и не полное время API. Признаки не требуют новых зависимостей/весов.

## Воспроизведение и защита от регрессии

```bash
.venv/bin/python scripts/train_scorer.py --vlm-confirmed --with-vlm
.venv/bin/python scripts/evaluate_zone_prototypes.py
.venv/bin/python -m pytest tests/test_zone_prototypes.py -q
```

Первый шаг регенерирует baseline rows и scorer стандартным способом. Второй
читает все 40, сверяет покрытие видео, идентичность кандидатов и существующие
desk/safe-признаки; при несовпадении требует регенерацию. Результаты в локальном
игнорируемом `data/zone_prototypes.json`; production weights второй шаг не пишет.
Для извлечения в обычном pipeline нужен `FORTE_ZONE_PROTOTYPES=1`, а для оценки
соответствующий stump должен быть явно включён; production модель их не содержит.

Исправлен существующий риск в train_scorer: лексикографическое `sc >= best`
позволяло компенсировать дополнительный FP уменьшением общей ошибки. Теперь
число ошибок **и** FP проверяются независимо. Regression test покрывает этот
случай; также проверены отсутствие сигнала при заслонении/недостатке кадров,
инвариантность census к сдвигу яркости, отбрасывание временного изменения,
отсутствие влияния замаскированных пикселей и отдельный пропуск ZNCC при
недостатке видимой площади его окна.

LOCO использовалась и для выбора признаков, поэтому это development-оценка,
а не независимая оценка неизвестных камер. Дополнительно общие кэшированные
перцептивные модели/трекер не переобучались внутри каждого fold. 0 FP на этих
19 нормальных видео не гарантирует 0 FP в эксплуатации.
