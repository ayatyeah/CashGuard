## 0. Вывод (TL;DR)

1. **Learned-модель «нормального визита» (n-gram / HMM) строить не на чём**: в 19 нормальных видео всего **9 визитов
   клиента в 6 видео** (Х-3, Х-5×2, Х-19×2, Х-35, Х-37, Х-39×2), остальные 13 нормальных — кассир один. Любая
   статистическая модель переобучится; «низкая вероятность» на ней — не защищаемый аргумент перед жюри.
2. Правильная рамка — **конформанс-проверка по шаблону процедуры** (van der Aalst: alignments, где *model move* =
   ожидаемый шаг не наблюдён, *log move* = лишний шаг/актор). Шаблон у нас не нужно учить — он **нормативный**:
   п. 19 № 231 задаёт порядок «идентификация → полистный пересчёт», п. 20 — «при клиенте / ранее принятые — в
   хранилище», п. 22 — «не покидать место при клиенте», п. 31 — выдача. 19 нормальных видео нужны не для обучения,
   а для **проверки FP = 0 каждого ограничения** (ровно так, как сейчас принимаются пни).
3. На токенах 2 fps грамматика визита **вырождается**: токен «контакт кистей» насыщается (запястья сидящего клиента и
   кассира всегда < 0.35 роста через узкий стол), «работа руками» шумит. Визит и у нормы, и у нарушений выглядит как
   `IN CONTACT OUT`. Различающее содержание есть только у (а) токенов сессии кассира (сидит / у сейфа / идёт / вышел),
   (б) плотной позы 8 fps (`probe_handover.py` — контакты с направлением), (в) токенов состояния зон (стол/сейф/дверь/экран).
4. Что реально даёт сигнал на новые типы с FP = 0 на 19 нормах (проверено): **C1** клиент ушёл до «работы»/раньше
   20 с (есть: `short_visit`), **C2** кассир отошёл > 0.9 роста, пока посетитель у стола (`client_remains`; на всех
   нормах 0 с — можно снять требование «не вернулся»), **C3** второй человек/стоящий посетитель во время визита
   (есть), **C4** посетитель в зоне кассира (d < 0.55 роста и стоя; нормальные клиенты сидят на 0.65–0.73 с ростом
   0.54–0.72 — 0 FP, новый), **C5** одиночный контакт до первой «работы» в полном визите (X-2; только 8 fps),
   **C6** «вышел без эпизода у сейфа + предметы/экран» (есть пни). **Не безопасно**: «передача кассир→клиент после
   пересчёта» — на норме Х-5 кассир возвращает документ (C→V 31.6 с после машинки) → без распознавания объекта
   (OWL «banknotes» vs «identity card») это FP.
5. Поэтому «Отклонение от типовой процедуры (требуется проверка)» выдаём **только по жёстким структурным
   нарушениям шаблона** (пропущен наблюдаемый шаг / лишний актор / нарушен порядок), никогда — по мягкому скору
   аномалии. Это согласуется с §3 отчёта 08 (ни одной «ловушки всего») и с FAQ B.9: баллы детекции (25) и
   локализации (15) за видео получаем, классификацию (15) честно отдаём оператору, подсказывая 1–2 ближайших типа.
6. Стоимость: ядро (`app/ml/grammar.py` + тип в `norms.yaml` + шаблон описания + регрессия на 40) — **6–8 ч**;
   плотная поза в окнах визитов — ещё **4–5 ч**; три дешёвых детектора на вероятные невиденные типы — по 2–3 ч.

## 1. Что говорит литература (и что из неё переносимо)

| Источник | Суть | Что берём |
|---|---|---|
| Конформанс-проверка (van der Aalst; Adriansyah; Bloemen et al.) — [обзор задач](https://arxiv.org/pdf/2507.11976), [alignments с milestones](https://pa.win.tue.nl/aligning-observed-and-modelled-behaviour-by-maximizing-synchronous-moves-and-using-milestones/), [vdaalst p1299](https://vdaalst.com/publications/p1299.pdf) | Трасса выравнивается с моделью: синхронный ход, **log move** (в трассе есть шаг, которого нет в модели), **model move** (модель требует шаг, которого нет в трассе); стоимость ходов задаётся явно; fitness = 1 − cost/worst. Alignments — де-факто стандарт. | Формулировка результата: «ожидаемый шаг X не наблюдён (model move)», «лишний актор (log move)». Стоимости — ручные, по наблюдаемости шага. Никакого обучения. |
| CaptainCook4D (NeurIPS 2024) — [paper](https://arxiv.org/pdf/2312.14556), [обзор ошибок 2025](https://arxiv.org/pdf/2510.19292) | 384 записи рецептов, ошибки: пропуск шага, нарушение порядка, техника, время, измерение… Распознавание ошибок по видео слабое даже на 94 ч данных. | Пропуск/порядок — единственные классы, которые ловятся по структуре; «техника» (пересчёт полистно vs «на глаз») — нет. Для нас: не обещать детекцию «как именно считал». |
| EgoPER (CVPR 2024) — [paper](https://khoury.northeastern.edu/home/eelhami/publications/cvpr24_EgoPER.pdf), [site](https://www.khoury.northeastern.edu/home/eelhami/egoper.htm) | Таксономия omission / addition / modification / slip / correction; обучение **только на безошибочных** видео; прототипы шагов + сегментация. | Таксономия отклонений для описания: «пропуск» (omission), «добавление» (лишний человек/объект), «изменение порядка». |
| IndustReal (WACV 2024) — [paper](https://openaccess.thecvf.com/content/WACV2024/papers/Schoonbeek_IndustReal_A_Dataset_for_Procedure_Step_Recognition_Handling_Execution_Errors_WACV_2024_paper.pdf) | Procedure Step Recognition: проверять **завершённость и порядок шагов**, а не действия; большинство ошибок — только в val/test (невиденные). | Ровно наша постановка (FAQ B.9). Шаги описываются как **состояния** (объект собран / деньги в сейфе), не как действия — у нас это состояние стола/сейфа/экрана. |
| Assembly101 mistakes — [Every Mistake Counts](https://arxiv.org/pdf/2307.16453), [PREGO](https://arxiv.org/pdf/2404.01933), [PROVIA](https://arxiv.org/pdf/2609.20638) | Даже с GT-метками действий recall ошибок ~63 %; ордер-ошибки ловятся графом предшествования, собранным из нормальных последовательностей; критика: позиционные приоры дают результат, близкий к SOTA. | Граф предшествования «ID → деньги → пересчёт → сейф → уход клиента» — это и есть наш шаблон; позиционный приор (клиент сидит ≥ 20 с) уже работает (`short_visit`). |
| Видеонаблюдение, abnormal event (one-class на нормах; обзор VAD в отчёте 08) | Метрики без порога скрывают FP; рабочую точку выбирают при фиксированном FPR. | Для «отклонения» порог не калибруем на AUC — требуем FP = 0 на 19 нормах, иначе ограничение не включается. |

Общий урок всех четырёх датасетов: **без примеров ошибок ловятся только структурные отклонения** (пропущенный
наблюдаемый шаг, лишний шаг, порядок), а не ошибки исполнения. Для кассы это означает: мы можем сказать «после
передачи денег клиент покинул помещение раньше, чем наблюдался пересчёт», но не «пересчёт был неполистным».

## 2. Шаблоны процедуры (нормативные, не выученные)

Три шаблона, по которым размечается любое видео. Шаги помечены наблюдаемостью на нашем стеке: **●** надёжно,
**◐** частично (нужна плотная поза/OWL), **○** не наблюдаемо (не утверждать).

**T1. Приём наличных от клиента (п. 19, 20, 22 № 231)**
```
V_ENTER ● → DOOR_CLOSED ● → V_SEATED ● → ID_HANDOVER(V→C) ◐ → CASH_HANDOVER(V→C) ◐
→ COUNT (машинка/вручную) ◐ → [DOC_RETURN(C→V) ◐] → SAFE (деньги убраны) ◐/● → V_LEAVE ●
инварианты: n_inside ≤ 2 ●; кассир у стола пока V у стола ●; V не в зоне кассира ●
```
**T2. Сессия кассира без клиента / закрытие (п. 20 ч. 2, 37, 80 № 231; п. 71 № 53)**
```
C_SEATED ● → [WORK ◐] → C_STAND ● → SAFE_OPEN/CLOSE (у сейфа ≥ 4–5 с) ● → [LIGHT_OFF ●] → C_LEAVE ●
постусловия после C_LEAVE: стол пуст ● (items/desk_change), экран погашен ●, сейф в исходном виде ● (safe_change), ключ не в замке ◐ (OWL)
```
**T3. Инкассация (п. 24, 25, 42 № 231)**
```
V_ENTER(с сумкой) ● → BAG_HANDOVER ◐ → INSPECT (посетитель остаётся ≥ 15 с) ● → [ID] ◐ → ... → COUNT ◐ → SAFE ●
```
Выдача (п. 31) зеркальна T1: `ID → SAFE(взять) → COUNT при клиенте → CASH_HANDOVER(C→V) → V_LEAVE` — её шаги ◐,
отдельный шаблон не вводим, пока нет плотной позы + OWL (см. §5, что небезопасно).

## 4. Эмпирика на 40 видео (проба `scripts/probe_grammar.py`)

**4.1. Сколько «нормы» у нас есть.** 19 нормальных видео: 13 без посетителя (кабинеты B, D, E, G), 6 с клиентами —
9 визитов, из них 2 обрезаны концом записи. Нарушений с визитом — 10 визитов в 9 видео.

**4.2. Грамматика визита (событийная, 2 fps).** Нормальные визиты: `IN CONTACT OUT` ×5, `CONTACT IN CONTACT OUT`,
`IN CONTACT WORK CONTACT OUT`, `CONTACT IN OUT`, `CONTACT IN CONTACT WORK OUT`. Нарушения: X-1, X-2, Х-34, Х-38×2,
Х-4×2 — `IN CONTACT OUT` (расстояние до ближайшей нормы **0.00**); Х-18 — `CONTACT IN SAFE CONTACT CROWD OUT`
(0.33, за счёт CROWD); Х-33 — `IN OUT` (0.33). Вывод: редактирующее расстояние по этим токенам **не отличает** 7 из 10
нарушений от нормы; выделяется только то, что уже ловят `crowd` и `entry`.

**4.3. Грамматика сессии кассира (одиночные видео).** Норма: Х-12 `S W F W F W F W F W -`, Х-23 `S W F W F W F -`,
Х-25 `S F W F -`, Х-27 `S W F W -`, Х-29 `S W F W F -`, Х-21 `F W S`, Х-31 `- W F W F S W F`. Нарушения: Х-11
`S F W F W -`, Х-15 `S F W F -`, Х-22 `S F W -`, Х-24 `S F W F W -`, Х-26 `S W F W F -`, Х-28 `S W F W -`.
**Порядок одинаков** — кассир во всех случаях подходит к сейфу перед уходом. Различает не порядок, а
**состояние после** (предметы/экран/сейф) и время у сейфа (`tidy`: норма 0.5–13 с, нарушения 0.5–7.5 с — само по себе
не разделимо, разделяет `unsecured = items/(1+tidy/5)` — уже пень `leave_items`). Грамматика здесь ничего не добавляет.

**4.4. Плотная поза 8 fps (`data/probe_handover.log`, 12 видео).** Контакты до первого длинного эпизода (≥ 5 с)
в полных визитах: Х-3 — 2 (C→V 7.2, ? 9.2), Х-5 — 2 (C→V 7.7, V→C 9.7), Х-19 — 2 (V→C 7.9, V→C 14.0), Х-16 — 2
(C→V 8.4, C→V 14.3), Х-37 — 2 (V→C 8.3, ? 9.1); **X-2 — 1** (10.2–15.8, единственный контакт за визит). Правило
«в полном визите (≥ 20 с) ровно один контакт до работы» → X-2 найден, 0 FP на 5 нормах с плотной позой. Это
**специфичный** тип `no_client_id` (он в train), а не generic — но тот же механизм даёт generic-событие, если контактов
нет вообще при визите ≥ 20 с.
Контр-пример к «возврат клиенту после пересчёта»: Х-5 (норма) — C→V 31.6–33.0 после машинки (9.7–27.2) и до сейфа
(46–52, сидя — токена SAFE нет). Это возврат документа. Без OWL на кропе передачи правило даёт FP → не включать.

**4.5. Прочие измерения на 40 видео** (для таблицы §5): минимальное расстояние посетителя до места кассира в нормах
0.65–0.73 роста при относительном росте 0.54–0.72 (все сидят); стоящие в зоне стола: Х-30 (0.46, 1.21), Х-17 (1.14, 1.30),
Х-33 (0.71, 1.30). «Кассир дальше 0.9 роста, пока посетитель у стола»: **0 с во всех 19 нормах** (Х-28: 1 с —
фантомный трек посетителя в пустой комнате; порог 4 с его отсекает). `desk_change` между визитами: нормы 0.01–0.04,
нарушения 0.04–0.05 — не разделимо без OWL. `door_change` у нормы Х-16 = 0.18 (входил посетитель) — гейт `standing`
(входил кассир) обязателен.

## 5. Ограничения шаблона: что включать, что нет

Каждое ограничение — один «model move»/«log move». Включается только при **FP = 0 на 19 нормах**.

|---|---|---|---|---|---|---|

| C5 | В полном визите ≥ 20 с — ≤ 1 контакт кистей до первой работы (нет пары ID → деньги) | T1: `ID_HANDOVER` пропущен | `CONTACT` 8 fps | X-2 | 0 на 5 нормах с плотной позой (нужно прогнать Х-35, Х-39) | **требует `handover.py`**, 4–5 ч |
| C6 | Кассир вышел; перед выходом не было ≥ 4 с у сейфа **и** на столе предметы / экран светится | T2 постусловия | `unsecured`, `screen` | Х-24, Х-26, Х-15, Х-11, Х-28 | 0 | **есть** (пни `leave_items`, `leave_screen`) |
| C7 | Следующий клиент вошёл, стол не вернулся к виду до предыдущего визита | T1: `SAFE` пропущен | `desk_change` + `owl_item` | Х-4, Х-38 | `desk_change` один — 1 FP (Х-19); с OWL — 0 | **есть** (`next_visit_owl`) |
| C8 | Дверь не вернулась к виду через 4–12 с после входа | T1/T2 | `door_change` | Х-32, Х-33, Х-30 | 0 с гейтом `standing` | **есть** |
| X1 | Передача C→V после пересчёта без сейфа («вернул деньги») | T1 порядок | `CONTACT(C→V)` | X-1 | **≥ 1 FP (Х-5: возврат документа)** | **не включать** без OWL «banknotes vs ID» на кропе передачи |
| X2 | «Работа» после ухода клиента (пересчёт без клиента) | T1 порядок | `WORK` | Х-34 | шум `WORK` на 2 fps во всех видео | **не включать** до периодичности 8 fps |
| X3 | Низкая правдоподобность по n-gram/HMM визита | — | все | — | не оценить (9 визитов) | **не делать** |

Итого **новых** срабатываний на невиденные типы дают C2 (расширение), C4 (новый) и C5 (плотная поза); остальные
ограничения уже есть и получают только общую «обёртку» — тип-фолбэк и описание со списком пропущенных шагов.

## 6. Скоринг отклонения

Alignment-стоимость визита/сессии считается, но **событие порождает только жёсткое ограничение**:

```
cost(visit) = Σ_i w_i · [C_i нарушено]      w: C1 1.0, C2 1.0, C3 1.0, C4 1.0, C5 0.8, C6 1.0, C7 0.8, C8 1.0
p_event = 0.6 если ровно одно жёсткое C_i;  0.75 если ≥ 2 независимых;  мягкие признаки (desk_change без OWL,
WORK на 2 fps, расстояние до шаблона) — только в info["grammar"] для UI/отладки, не в события.
```
Таймкод = момент, когда пропуск шага стал фактом (конвенция организаторов и отчёта 08 §4): C1 — выход клиента −3 с
(как сейчас), C2 — кассир пересёк 0.9 роста, C4 — первый кадр посетителя в зоне, C5 — первый кадр работы (пересчёта)
без второго контакта (X-2: кассир берёт деньги на 10 с — совпадает с разметкой), C7 — вход следующего −3 с.
Доказательные кадры: `t−3`, `t`, `t+5…10`.

Дедупликация: если по тому же визиту сработал **специфичный** детектор (пень/правило с type_id), generic-событие
подавляется (`pipeline.run`: дедуп по времени ± 6 с расширить на пару «специфичный > generic»). Лимит ≤ 3 событий
на видео сохраняется.

## 7. Формулировка для жюри (без выдуманного типа)

Новая запись в `app/rules/norms.yaml` (цитаты — уже сверенные в файле, дословные):

```yaml
procedure_deviation:
  title: "Отклонение от типовой процедуры кассовой операции (требуется проверка)"
  observable: "Наблюдаемая последовательность действий не содержит шага, обязательного по Правилам № 231, либо содержит лишнего участника/действие"
  conditions: "Нарушено хотя бы одно структурное ограничение шаблона операции (пропущен наблюдаемый шаг, нарушен порядок, лишний актор)"
  exclusions: "Шаг мог быть выполнен вне поля зрения камеры — указывается явно; конкретный тип определяет оператор"
  document: "Правила осуществления кассовых операций… (постановление Правления НБРК от 29.11.2019 № 231)"
  clause: "п. 19 подп. 1), 2); п. 20; п. 22; п. 31 подп. 1), 4) — в зависимости от пропущенного шага"
  url: "https://adilet.zan.kz/rus/docs/V1900019680"
  quote: "Наличные деньги принимаются и пересчитываются кассовым работником в присутствии клиента."
  interpretive: true
  train_examples: {}
  enabled: true
  source_verified: true
```

Шаблон описания (в `pipeline.TEMPLATES`, факты подставляются из `Event.f` — только измеренное):

```
Наблюдается: посетитель подходит к столу кассира в {t_in:.0f} с; зафиксированы шаги: {steps_seen}.
Не наблюдается: {steps_missing} (ожидается по типовому порядку операции до {t:.0f} с).
Квалификация: отклонение от типовой процедуры кассовой операции — конкретный тип нарушения требует проверки оператором;
ближайшие типы по признакам: {hint_types}.
Норма (связанное требование): Правила … № 231, {clause}. Цитата: «{quote}».
Оговорка: шаг мог быть выполнен вне поля зрения камеры. Результат — подсказка для проверки человеком, не юридическое заключение.
```
Примеры подстановки: C2 → `steps_missing = «присутствие кассира у рабочего места до окончания обслуживания»`,
`clause = п. 22`, `hint_types = cashier_left_client_waiting`. C5 → `steps_missing = «передача документа клиентом до
передачи наличных (вторая передача не зафиксирована)»`, `clause = п. 19 подп. 1)`, `hint_types = no_client_id`.
C4 → `steps_missing = «посетитель остаётся на клиентском месте»`, `clause = № 14 п. 16 подп. 4) (по аналогии)`,
`hint_types = unauthorized_person`.

Политика «специфичный vs generic»: специфичный type_id, если сработал его детектор; `procedure_deviation`, если
сработало только ограничение шаблона. Для невиденного типа жюри классификацию мы теряем в обоих случаях, но детекцию
и локализацию (до 40 из 55 «весовых» баллов видео) — получаем; `hint_types` в описании оставляет шанс на зачёт типа
человеком. Слово «аномалия» и вероятности в тексте не употреблять.
