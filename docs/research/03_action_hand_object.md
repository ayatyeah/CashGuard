# 03 · Распознавание действий и взаимодействия «рука–объект» (CPU / Apple Silicon, разрешительные лицензии)

Агент №3 из 10. Дата: 2026-10-17. Источники — страницы GitHub/HF/arXiv (ссылки внизу каждого раздела). Модели не запускались,
`data/` не открывалась. Числа скорости на CPU — опубликованные (i7-11700, ORT) либо оценки по GFLOPs; на M3 Pro ожидаемо ×1.3–2 быстрее.

Цель трека: закрыть пропуски, которые не видны текущими признаками «сцена/стол/дверь»:
**передача денег без ID (X-2), деньги отданы клиенту (X-1), сумка убрана без пересчёта (X-13/Х-17), смешение пачек (Х-4/Х-38, Х-44)**,
а также дать общий механизм для нарушений, которых нет в train (жюри это обещает).

## 0. Главный вывод (TL;DR)

1. Все «тяжёлые» видеотрансформеры с чистой лицензией на **веса** можно пересчитать по пальцам: **X-CLIP (MIT)**, **InternVideo2 (Apache-2.0, 1B — не для CPU)**,
   **ViCLIP (MIT, ViT-L)**, **V-JEPA 2 (MIT, ViT-L/64 кадров — слишком дорог на CPU)**, **UniFormerV2 (Apache-2.0 код, веса без отдельной оговорки)**,
   **MoViNet (Apache-2.0)**, **X3D/SlowFast из PyTorchVideo (Apache-2.0)**, **torchvision video (BSD-3; веса «могут наследовать условия датасета» — Kinetics)**.
   **VideoMAE / VideoMAE v2 (веса CC-BY-NC-4.0), TimeSformer (CC-NC-4.0), Hiera (веса CC-BY-NC-4.0)** — исключены.
2. Скелетные модели (ST-GCN/PoseC3D/CTR-GCN) с весами на **NTU RGB+D — нельзя**: условия NTU прямо запрещают коммерческое использование и
   «derivation» датасета. Единственные «чистые» скелетные веса — PoseC3D на Kinetics-400 (47% top-1, бесполезны для наших классов).
   Вывод: скелетную ветку делать **своими инженерными признаками**, а не предобученными классификаторами.
3. Hand–object детекторы: **100DOH `hand_object_detector` — код MIT, но веса без лицензии, сборка под CUDA, датасет из YouTube**; **EgoHOS — MIT код, Swin-L
   (тяжело), эгоцентрические данные**; **HOT3D — лицензия Meta, не наш случай**. Для нас практичны только **RTMPose-hand / RTMW (Apache-2.0, rtmlib)** и
   **MediaPipe Hands (Apache-2.0; в model card «рука с предметом» и «surveillance» объявлены out-of-scope — не юридический запрет, а предупреждение о качестве)**.
4. Ни одна из моделей не имеет опубликованных оценок на **верхней CCTV-камере в масштабе ~1 м**; ближайшие работы (потолочные камеры Volvo/Chalmers,
   FlyPose) показывают, что без дообучения качество падает. Наши ракурсы (behind/front/corner) — не строго «сверху», кисти в основном видны, поэтому
   RTMPose-кисти как источник траекторий — реалистично; проверять на своих 40 видео обязательно.

## 2. Топ-5 подходов под наши пропуски (подробно)

### №1. Детектор передачи («handover») только по позе + грамматика визита
- **Что закрывает.** X-2 (деньги без ID): в норме перед пересчётом **две** передачи клиент→кассир (ID, потом деньги; Х-3: ID 7–11 с, деньги 12–13 с), в
  нарушении — **одна**. X-1 (деньги отданы клиенту): передача **кассир→клиент после эпизода пересчёта**. X-13/Х-17 (сумка без пересчёта): передача крупного
  объекта клиент→кассир, после которой нет эпизода пересчёта/машинки, а посетитель уходит < 15 с (уже есть правило «короткий визит» — передача даёт точный таймкод и
  убирает зависимость от VLM «клиент передаёт сумку»). Х-18 (второй человек передаёт карточку) — тоже передача, подтверждает «посторонний».
- **Лицензия.** Полностью на имеющемся стеке (YOLOX + RTMPose-m, Apache-2.0); DTW — dtaidistance (Apache-2.0).
- **Усилия.** 2–3 дня: поднять частоту позы в окнах визита с 2 до 6–10 fps, вычислить признаки §3, разметить ~25 эпизодов передач по `train_timelines.md`, подобрать пороги LOCO.
- **Ожидаемый выигрыш.** +3–4 видео из 7 пропусков при 0 FP (X-2, X-1, Х-13/Х-17); таймкод ±1 с.
- **Риски.** (а) В X-2 клиент **кладёт деньги на стол, кассир берёт** — это передача «через стол», не «из рук в руки» → детектор должен ловить оба типа (§3.3);
  (б) RTMPose на сильно наклонной камере может путать левое/правое запястье и терять кисть под столом — брать `min` по парам запястий и фильтр по уверенности ≥0.5;
  (в) передача ID по позе неотличима от передачи денег → решается порядком/счётом событий и, при желании, №5.
- **Литература.** Фазы передачи (reach–transport–transfer–end), фаза собственно трансфера 0.5–0.64 с, «отдающий задаёт тайминг», точка передачи — посередине между
  участниками: [систематический обзор Frontiers 2023](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2023.1147296/full); длительность всей передачи
  3.3–3.6 с на 2 720 сидячих передачах: [HOH](https://arxiv.org/html/2310.00723v5); распознавание жеста передачи по кейпоинтам + объект + голова, >90% (человек→робот):
  [arXiv 2007.09945](https://arxiv.org/pdf/2007.09945); запястья как якорь для поиска предмета в руке: [SHOP](https://arxiv.org/abs/2203.15228).

### №2. Состояния рук кассира по кистям (RTMPose-hand / RTMW-m / MediaPipe)
- **Что закрывает.** Эпизоды «ручной пересчёт», «машинка», «у сейфа», «пишет/ноутбук». Из них собираются: «сумка убрана без пересчёта» (передача сумки → нет
  пересчёта → сейф/стол), «пересчёт без клиента» (уже есть, станет точнее), «деньги отданы клиенту» (пересчёт → передача к клиенту), частично «смешение пачек»
  (две пачки от двух клиентов без эпизода «сейф» между ними — косвенно; Х-44 «отбраковка в пачку» — рука к верхнему карману машинки, затем к пачке: слабый сигнал).
- **Признаки.** Для каждого запястья кассира (RTMPose-m) и 21 точки кисти (RTMPose-hand 256² на кропе у запястья, либо RTMW-m сразу 133 точки):
  - *ручной пересчёт*: обе кисти над столом, расстояние между кистями 0.3–0.9 S (S — ширина плеч кассира), спектр скорости кончиков пальцев/запястья с пиком
    1.5–4 Гц, длительность ≥3 с (в Х-3/Х-4 ручной пересчёт 6–8 с; окно анализа 2 с с шагом 0.5 с);
  - *машинка*: кисть в ROI машинки (ROI — из YOLOX/CLIP или задаётся как кластер положений кисти в «behind/front» ракурсах), изменение пикселей ROI;
  - *сейф*: корпус у зоны сейфа (есть) + вытянутая рука (reach ≥0.7 длины руки) в сторону от камеры/стола;
  - *телефон/напиток*: предмет (YOLOX `cell phone`/`cup`) в радиусе 0.25 S от кисти + поза «кисть у головы» (напиток: подъём кисти к уровню носа).
- **Лицензия.** Apache-2.0 (rtmlib: RTMPose-hand Hand5 2.58 GFLOPs; RTMW-m 4.3 GFLOPs). MediaPipe Hands Apache-2.0 — запасной; в model card предупреждение, что
  руки с предметами — вне области применения, а также «surveillance out of scope» (это заявление о назначении, не условие лицензии, но для чистоты лучше RTMPose).
- **Усилия.** 3–4 дня. **Выигрыш:** эпизодная «временная шкала операций» для всех типов; **Риск:** кисти 30–60 px в 464×848 — точки пальцев шумные, поэтому
  основные признаки строить на запястьях и центре кисти, пальцы — только для частотного признака.

### №3. X-CLIP (MIT) как zero/few-shot скорер клипов
- **Идея.** На кандидатных окнах 2–3 с (из №1/№2 или скользящим окном 1 с при посетителе у стола) вырезать кроп рабочей зоны/вокруг запястий, 8 кадров 224²,
  получить видеоэмбеддинг X-CLIP-B/32; (а) zero-shot: сравнить с текстами «a person counting banknotes by hand», «a cashier handing money to a client»,
  «putting money into a safe», «emptying a bag onto the desk», «using a money counting machine», «a person using a phone», «drinking»; (б) few-shot
  «прототипы»: эмбеддинги 1–3 наших примеров на класс (X-1, X-2, Х-13, Х-44…) и ≥30 нормальных клипов → ближайший прототип с запасом (margin) к
  нормальным; порог калибруется LOCO на 19 нормальных видео так, чтобы FP = 0.
- **Почему X-CLIP, а не CLIP по кадрам (который уже пробовали).** Кросс-кадровое внимание даёт движение (считать/передавать — это движение, не вид стола);
  в статье при K=2 X-CLIP-B/16 даёт 53.0% на HMDB против 20.9% у Swin-B (переобучение одномодальных моделей), zero-shot HMDB 44.6 / UCF 72.0 / K600 65.2.
- **Лицензия.** MIT код и веса; обучен на Kinetics-400 (CC BY 4.0 — официальный текст не получен, см. §5).
- **CPU.** B/32 8 кадров ≈ 36 GFLOPs → ~0.3–0.6 с/клип на M3 Pro; 100 кандидатных клипов на видео — 30–60 с. B/16 (145 GFLOPs) — только если B/32 не хватает.
- **Усилия.** 2 дня (HF `transformers` уже в стеке). **Выигрыш:** единственный способ хоть как-то реагировать на **типы, которых нет в train**; **Риск:** доменный
  разрыв и ложные срабатывания — поэтому использовать только как *подтверждение* кандидатов из №1/№2 (ансамбль согласия, как уже сделано с VLM), а не как первичный детектор.

### №4. Компактный Kinetics-классификатор как слабый временной признак
- X3D-S (PyTorchVideo, Apache; 2.96 GFLOPs, 13 кадров, K400 73.3%) или MoViNet-A0/A2 stream (Apache; 2.7/10 GFLOPs, K600 72/78%; stream-версия — 16–66 мс/кадр на
  одном ядре x86). Снимать по кропу кассира скользящим окном 1 с вероятности `counting money`, `texting`, `talking on cell phone`, `looking at phone`, `drinking*`,
  `shaking hands`, `opening door`, `using atm`, `writing`, `using computer` → сглаженные временные ряды → признаки для существующих пней (например, «доля времени
  `counting money` после ухода клиента»).
- **Усилия.** 1–2 дня. **Выигрыш:** дешёвая вторая точка зрения для «пересчёт», «телефон», «напиток», «дверь»; эмбеддинг (2048-d) — для прототипов из №3.
  **Риск:** доменный разрыв (Kinetics снят с уровня глаз); не вводить в финальный скорер, если ухудшает LOCO (как уже делалось с VLM-признаками).
- Примечание: веса PyTorchVideo/torchvision не имеют отдельной лицензии; torchvision явно пишет, что веса «могут наследовать условия датасета» — у Kinetics это CC BY 4.0.

### №5. Объект в руке через open-vocabulary детектор (OWLv2 / Grounding DINO, Apache-2.0)
- В моменты, найденные №1 (±1 с) и в «стол после ухода клиента», запускать OWLv2-B/16 на кропе 2×S вокруг запястий с запросами `banknotes`, `stack of money`,
  `ID card`, `passport`, `money bag`, `key`, `phone`, `cup`. Даёт **содержание** передачи (ID vs деньги) → X-2 решается напрямую, X-1 различает «вернул ID» от «вернул
  деньги», X-22 (ключ в замке сейфа — запрос `key` в ROI замка после ухода), X-4/Х-38 (деньги на столе при входе следующего клиента — уже есть сигнал, детектор
  может заменить YOLOX-«предметы», который давал FP).
- **CPU.** Тяжело (OWLv2 960², ~секунды на кадр) → строго точечно, ≤20 кадров на видео. **Усилия:** 2–3 дня. **Риск:** купюры/ID мелкие (10–40 px); нужно проверить
  recall на кадрах из `train_timelines.md`, прежде чем закладываться. OWLv2 на HF помечен как «research output» — это описание назначения, лицензия Apache-2.0.

## 3. Конкретный дизайн «детектора передачи» только по позе

### 3.1 Входы и частота
- Треки людей (есть), 17 точек RTMPose-m (есть). Запястья: kp 9 (левое), 10 (правое); локти 7/8; плечи 5/6; бёдра 11/12.
- **Частота:** фаза собственно трансфера длится ~0.5–0.65 с, вся передача ~3.3 с → при 2 fps событие пропускается. Включать «плотную позу» **6–10 fps только в
  окнах, когда посетитель у стола** (трек-классификатор уже выделяет визит). Стоимость: RTMPose-m 11 мс/человек (i7) × 2 человека × 8 fps ≈ 0.18 с на секунду визита.
- **Нормировка (камеро-независимая):** S = медианная ширина плеч кассира в пикселях (или уже используемая единица — рост кассира H; S ≈ 0.25 H). Длина руки
  L = медиана (|плечо–локоть| + |локоть–запястье|) по треку. Все расстояния — в единицах S, скорости — S/с.
- Сглаживание запястий: медианный фильтр 3 кадра + линейная интерполяция пропусков ≤2 кадра; точки с уверенностью < 0.4 выбрасываются.

### 3.2 Покадровые признаки для пары (кассир C, посетитель V)
1. `d_ww` = min по 4 парам запястий ||w_C − w_V|| / S.
2. `reach_C`, `reach_V` = max по двум рукам ||w − плечо той же руки|| / L (0 — рука у тела, ~1 — вытянута).
3. `toward_C`, `toward_V` = косинус между вектором «плечо→запястье» и вектором «своё плечо→центр торса партнёра» (рука направлена к партнёру).
4. `v_C`, `v_V` = скорость активного запястья (S/с); знак — к партнёру (+) / от партнёра (−) по проекции на линию торсов.
5. `mid_ok` = точка контакта (середина между ближайшими запястьями) лежит в полосе между торсами (проекция на линию торс–торс в [0.25, 0.75]) и в зоне стола
   (по y — между линией плеч кассира и линией бёдер посетителя; зона стола уже есть в пайплайне).
6. `h_rel` = высота запястья над «уровнем стола» (стол ≈ уровень локтей сидящего кассира в покое) — отличает «над столом» от «на столе».
7. Для передачи через стол: `in_cell_C(t)`, `in_cell_V(t)` — принадлежность запястья ячейкам сетки 3×3 над столом (ячейки размером ~0.5 S).

### 3.3 Логика события (конечный автомат, оба типа передачи)
**A. Из рук в руки (direct):**
- *approach:* в течение ≤1.5 с `d_ww` падает ниже 0.8 и `reach` хотя бы одного ≥ 0.6, `toward` ≥ 0.5;
- *contact:* `d_ww` < **0.45** (≈ 18 см при S≈40 см) непрерывно **0.25–2.0 с**, `mid_ok` = true;
- *retract:* в течение ≤1.5 с после контакта `d_ww` > 0.8 и оба `reach` падают ниже 0.5;
- *cooldown* 1.5 с; события ближе 1.5 с сливаются.
**B. Через стол (desk-mediated):**
- запястье V входит в ячейку стола с `reach_V` ≥ 0.6 и выходит (пребывание 0.2–3 с), после чего в **≤4 с** в ту же или соседнюю ячейку входит запястье C с
  `reach_C` ≥ 0.5 и выходит; направление V→C. Симметрично C→V (кассир положил — клиент взял). X-2 (9.0–9.7 клиент кладёт, 10.0–10.7 кассир берёт) — ровно этот шаблон.
**Направление (кто отдаёт)** для A: отдающий — тот, чья рука (i) начала движение к партнёру раньше (по порогу `v` > 0.5 S/с), (ii) достигла точки контакта первой,
(iii) ушла от точки контакта первой после разрыва (получатель чаще тянет предмет к себе/к машинке). Голосование 2 из 3; при равенстве — «неопределено» (событие
учитывается без направления). Обоснование: по литературе отдающий задаёт тайминг и начинает отпускать синхронно с касанием получателя.
**Объект (опционально):** YOLOX `handbag/backpack/suitcase` в радиусе 0.5 S от точки контакта → `object=bag`; иначе `object=small` (ID/деньги неразличимы по позе → №5).

### 3.4 Грамматика визита → нарушения
Для каждого визита (вход посетителя → уход) строим последовательность событий: `T(V→C, small)`, `T(C→V, small)`, `T(V→C, bag)`, `COUNT_hand`, `COUNT_machine`,
`SAFE`, `LEAVE_V` (эпизоды пересчёта — из №2 или из текущих эвристик «кисти у машинки», `SAFE` — есть).
- **no_client_id (X-2):** первый `COUNT_*` наступил, а до него ровно **одна** `T(V→C)`; эталон Х-3 даёт две. Порог: ≥2 передачи до пересчёта = норма.
  Защита от FP: если ID положен на стол ещё до того, как трек-классификатор признал визит (клиент заходит с документом в руке) — учитывать события с момента
  входа в комнату, а не с «подхода к столу».
- **cash_handed_back (X-1):** `T(C→V)` после `COUNT_*` и до `LEAVE_V`, при этом **нет** `SAFE` между `COUNT` и `T`; возврат ID в норме случается *до* пересчёта
  или сразу после `T(V→C)` №1 — исключается порядком. Если доступен №5 — требовать `object≠ID`.
- **collection_bag_no_check (Х-17/Х-13):** `T(V→C, bag)` и затем в ближайшие 60 с нет `COUNT_*`, посетитель уходит < 15 с (есть правило) — передача даёт таймкод
  и убирает зависимость от VLM.
- **count_not_in_client_presence (Х-34):** `LEAVE_V` раньше первого `COUNT_machine` — уже есть, но теперь с точным моментом передачи денег.
- **unauthorized_person (Х-18):** `T(V2→C)` при сидящем V1 — усиливает текущий детектор.
- **cash_left_on_desk / mixed (Х-4, Х-38):** вход V2 при отсутствии `SAFE` после `COUNT` визита V1 → кандидат; подтверждение — №5 на столе в момент входа V2.
  Честно: по позе это не детектируется, только по состоянию стола.
- **rejects_merged (Х-44):** вне возможностей позы; единственный кандидат — №3 (прототип из одного примера) с подтверждением «нет детектора/лампы» (есть в описаниях Х-43/45).

### 3.5 Валидация на 40 видео
1. **Разметка событий передачи** по `docs/train_timelines.md` (не открывая `data/` заново, таймкоды уже выписаны): X-2 (9.0–10.7, через стол), Х-3 (7–11 ID, 12–13
   деньги), Х-4 (11–18 ID, 20–24 деньги, 60–63 ID, 65–66 деньги), Х-17 (6.3–8.3 сумка), Х-18 (6–7.75, 20.3–21), Х-34 (6.7–8.3), Х-35, Х-37, Х-39 (две серии),
   Х-5. Итого ~25 положительных интервалов; отрицательные — все остальные секунды визитов + 13 «corner»-видео с кассиром в одиночестве (там событий быть не должно).
2. **Метрики:** событийные precision/recall при допуске ±1.5 с; FP на минуту вне интервалов; точность направления на размеченных событиях; доля
   «direct» vs «desk-mediated» (ожидаем в behind-ракурсе преимущественно через стол).
3. **Протокол:** пороги (`0.45`, `0.25–2.0 с`, `reach 0.6`, `4 с` для через-стол) подбираются **leave-one-cabinet-out** — ровно так же, как `scorer.json`; цель
   recall ≥ 0.9 на событиях при FP ≤ 0.1/мин. Затем грамматика §3.4 подаётся в скорер как новые признаки-пни; принимается только если LOCO-точность вердикта не падает
   и FP = 0 (тот же критерий, что для VLM-признаков).
4. **Стресс-тесты на новый ракурс:** зеркальная копия и зум 12% уже есть (`scripts/augment_videos.sh`) — для событий передачи они корректны (расстояния нормированы
   на S), в отличие от яркостных признаков; проверить, что события не исчезают.
5. **Диагностика кистей сверху:** на 2–3 видео каждого «кабинета» визуально проверить, не меняются ли местами запястья у кассира, когда камера «behind»; при
   проблемах использовать `min` по парам (уже заложено) и игнорировать left/right.
