# 08. Тактика набора баллов: автооценка по API + питч для шортлиста

Агент исследования #8 из 10. Дата: 17.10.2026. Исходные документы: `docs/research/CONTEXT.md`, `docs/ml_model.md`,

## 0. Как устроен процесс и куда «утекают» баллы

| Критерий | Баллы | Как, вероятно, считается | Что гейтит |
|---|---|---|---|
| Детекция (вердикт) | 25 | доля из 5+ видео с верным `verdict` | работающий API, таймаут 5 мин |
| Локализация | 15 | `timecode_sec` в допуске к разметке (по опыту челленджей — ±5–10 с) | только для найденных нарушений |
| Классификация | 15 | `type` совпал с разметкой | только для найденных нарушений |
| Нормативная база | 15 | ссылка на НПА и описание — по видимости, ручная проверка жюри | почти не зависит от CV |
| Устойчивость к новому ракурсу | 10 | отдельное видео с незнакомого ракурса | нет ложного/есть верный вердикт |
| Продукт | 10 | UI, сценарий использования, демо | питч |
| Техника | 10 | код, запускаемость, лицензии, локальность | репозиторий + питч |

Выводы, которые определяют приоритеты:

1. **55 баллов (детекция + локализация + классификация) защищены одним условием — API отвечает по контракту ТЗ за 5 минут.**
   Любая ошибка контракта обнуляет их для всех видео сразу. Это единственная «бинарная» статья бюджета.
2. Локализация и классификация считаются только по найденным нарушениям, то есть **пропуск стоит до 55/N баллов за одно
   видео** (при N=5 — до 11 баллов), а ложное срабатывание на нормальном видео — 25/N (≈5 баллов) плюс репутационно у жюри.
   Формулировка организаторов («пропуски недопустимы, ложные — минимальны») подтверждает асимметрию ≈2:1 в пользу recall.
3. **Нормативная база (15) — самая «дешёвая» статья**: она не зависит от качества детектора, а только от аккуратности
   таблицы норм и шаблона описания. Это надо добить до максимума в первую очередь.
4. В тесте «могут быть типы нарушений, не встречавшиеся в обучении» — значит, часть пропусков неизбежна, и на питче важнее
   показать, *почему* система промолчала (не выдумала), чем обещать 100 % recall.

Аналогия из литературы: в AI City Challenge (трек аномалий) метрика S4 = F1 × (1 − NRMSE по времени старта); допуск
±10 с; лишние предсказания рядом с тем же событием считаются **ложными**; победитель 2021 (Baidu) получил F1 0.95
при RMSE 5.3 с за счёт (а) масок «где аномалия вообще возможна», (б) консенсуса двух детекторов, (в) минимальной
длительности состояния, (г) **обратного поиска момента начала** (backtracking: разметка ставит старт на момент *удара*,
а не остановки машины). Все четыре приёма переносятся на кассу один в один.

## (a) 10 тактик, ранжированных по ожидаемому приросту баллов

### 1. Контракт API + нагрузочный прогон «как жюри» — защищает до 55 баллов
**Ожидаемый прирост:** P(сбой) × 55. Даже при P = 20 % это ≈11 баллов — больше любой ML-тактики.
Что сделать (по `api_contract_gap.md`):
- маршруты `POST /api/v1/analyze` (multipart, поле **`file`**) и `GET /api/v1/jobs/{job_id}`; статусы наружу строго
  `processing | done | failed` (`queued` → `processing`); заголовок `X-API-Key`; `DEMO_MODE=false` жёстко в прод-конфиге,
  а лучше — удалить ветку демо-события из прод-сборки, чтобы «выдуманное событие» физически не могло уйти жюри;
- **конкурентность.** Жюри может загрузить 5+ видео подряд за минуту. При одном воркере и ≈1× реального времени пятое
  видео (до 145 с) выйдет из очереди через >8 мин — провал по таймауту. Нужны либо N воркеров (на M3 Pro 18 ГБ — 2–3
  параллельных процесса, модели ONNX ~1–2 ГБ каждый), либо гарантированный бюджет: анализатор уже считает дедлайн от
  mtime файла и переходит в `cheap`-режим — проверить, что при 5 одновременных загрузках **все** успевают в 5 мин и
  возвращают `done`, а не `failed`;
- при исчерпании бюджета возвращать **частичный, но валидный** результат (`done`, вердикт по уже обработанной части),
  а не `failed`: `failed` = гарантированный ноль по видео, частичный результат = шанс;
- `violations: []` (не `null`) при `no_violation`; `image_base64` без `data:` префикса; JPEG; числовые `timecode_sec`;
  `timestamp_sec` ≤ длительности; UTF-8; никаких `NaN`.
Источники: правила AI City (формат, лимит предсказаний, FP за дубли) — https://www.aicitychallenge.org/2021-data-and-evaluation/ ;
практика тестирования контрактов — https://101techlabs.com/guides/developer-tools/common-api-testing-errors

### 2. Нормативная база как выверенная таблица + шаблон «наблюдаю / вывод / норма» — до 15 баллов
**Ожидаемый прирост:** 5–10 баллов (сейчас `norms.yaml` есть, но жюри будет читать описания глазами).
- Для каждого `type` — точная ссылка: НПА (Постановление Правления НБРК о кассовых операциях, внутренние правила
  банка), **номер пункта**, короткая цитата. Ни одного придуманного номера пункта: лучше «п. X Правил…» с проверкой по
  `docs/normative_sources.md`, чем правдоподобная выдумка — жюри-банкиры узнают свои документы.
- Шаблон описания из трёх частей, генерируется из фактов детектора, не LLM-фритекстом:
  `Наблюдается: кассир покинула рабочее место в 00:47, экран ПК остался активным (кадры 1–3). Квалификация:
  незаблокированное рабочее место при отсутствии кассира. Норма: … п. …`.
  Факты — только то, что реально измерено (например, «предметы на столе», а не «наличные», если детектор не различает
  купюры). Отдельно помечать вывод: «предположительно наличные (пачка в зоне пересчёта)».
- Это же защищает критерий «без выдуманных утверждений»: в литературе по инцидент-репортам рекомендуют привязывать
  каждое утверждение к структурированному наблюдению и помечать выводы отдельно (DeepFaith, GSAR — ссылки ниже).

### 3. Рабочая точка под асимметрию 2:1 (пропуск дороже ложного) — до 10 баллов детекции
**Ожидаемый прирост:** +1–2 верных вердикта из 5 (≈5–10 баллов), если recall вырастет с 0.62 без роста FP > 1 на 40.
- Сейчас пороги выбирались как max-margin пни при FP = 0. Перебрать порог каждого типа на leave-one-cabinet-out с
  **ценовой функцией** `loss = 2·FN + 1·FP` (вес отражает формулировку ТЗ) и взять минимум. Там, где признак
  разделим с запасом, порог не изменится; где позитивы «на грани» (дверь, деньги на столе) — сдвинется в сторону recall.
- Подход «зафиксировать бюджет пропусков, затем читать FP» — стандарт в видеонаблюдении (FR5: FP при FN = 5 %);
  AUC как метрика «не знает» о рабочей точке — решение всегда одно и его надо выбирать явно.
- Не включать «ловушку всего» (generic-аномалии) ради неизвестных типов: на тесте VLM-2B дала FP на нормальных видео,
  а каждое ложное на нормальном видео — −5 баллов и минус доверие жюри. Лучше честный пропуск + слайд «что система не
  видит и почему».
Источники: https://arxiv.org/html/2508.14203v1 (обзор VAD: метрики без порога игнорируют FP);
https://arxiv.org/pdf/2608.21244 (оценка при фиксированном FPR); https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12620233

### 4. Таймкод = момент, когда нарушение становится фактом; калибровка смещения по типам — до 15 баллов локализации
**Ожидаемый прирост:** 3–6 баллов (перевод «вердикт верный, таймкод мимо» в полный зачёт).
- Конвенция разметки организаторов (из `ml_model.md`): «уход» отмечают **у двери**, а не при вставании. Общее правило
  действующих челленджей: таймкод — **онсет** события в понимании разметчика (у Baidu: момент удара, а не остановки;
  в SoccerNet/DFL — момент контакта с мячом). Для нарушений-состояний (стол без присмотра, дверь открыта, сейф открыт)
  это момент, когда состояние *стало* нарушением (кассир пересекла дверь; дверь осталась открытой > N с; кассир отошла от
  открытого сейфа), для нарушений-действий (напиток, телефон, передача денег) — первый кадр действия.
- По 40 размеченным видео посчитать **систематическое смещение per type** (медиана `pred − gt`) и вычесть его.
  Медиана ошибки 2.0–2.5 с при вероятном допуске ±5 с — уже хорошо, но хвост (до 5 с) опасен; смещение убирает хвост
  дёшево.
- Три evidence-кадра: `t−3 с` (контекст до), `t` (онсет), `t+5…10 с` (состояние после) — так жюри видит причинность и
  принимает таймкод даже при расхождении в 2–3 с.
Источники: https://arxiv.org/html/2505.03991v1 (окна допуска: tight 1–5 с, loose 5–60 с);
AI City 2021 (±10 с, NRMSE по старту); Baidu backtracking (arXiv 2105.03827).

### 5. Политика выдачи событий: одно главное событие на нарушение, ≤3 на видео, без дублей — защищает 15 классификации
**Ожидаемый прирост:** 2–5 баллов (убирает «неправильное событие при правильном вердикте», как Х-13 на тесте).
- Сортировать `violations` по уверенности; первое — то, по которому принят вердикт. Если жюри сопоставляет ближайшее
  событие к разметке — порядок не важен, если берёт первое — критичен. Ставить главное первым безопасно в обоих случаях.
- Не выдавать два события одного типа ближе 10 с; не выдавать событий, не повлиявших на вердикт (в AI City каждый
  «лишний» прогноз = FP; в SoccerNet дубли внутри окна давят precision — все победители применяют NMS/Soft-NMS и top-M).
- Второе-третье событие — только если это **другое** нарушение с независимым признаком (например, уход + незаблокированный
  экран). Это повышает шанс совпадения типа с разметкой, когда организаторы квалифицировали эпизод иначе, и
  не считается FP на уровне вердикта.
- Имена `type` сверить с перечнем из ТЗ **посимвольно** (если в ТЗ есть enum — это тот же класс ошибок, что и имена полей).
Источники: https://arxiv.org/pdf/2309.06006 (SoccerNet 2023: NMS как ансамбль), https://arxiv.org/pdf/2206.07846

### 6. Самопроверки на новом ракурсе + плавная деградация + своя съёмка — до 10 баллов устойчивости
**Ожидаемый прирост:** 3–7 баллов; дополнительно это сильнейший слайд питча (единственная команда с измеренной
устойчивостью по 7 ракурсам).
- Пайплайн уже camera-agnostic (признаки в долях роста кассира, место — из сидячего эпизода). Добавить **явные тесты
  пригодности сцены** на входе: кассир найден (трек ≥ X % длительности), место определено, рост в пикселях в разумном
  диапазоне, ориентация кадра (портрет/ландшафт), fps/разрешение/кодек (HEVC в .mov!). Если проверка не прошла —
  **safe-mode**: отключать детекторы, зависящие от не найденных якорей (дверь не видна → `door_left_open` не формируется —
  уже так), вердикт по оставшимся; в доп. поле `scene_checks` писать, что именно не найдено. Пропуск лучше ложного,
  а объяснённый пропуск лучше молчаливого.
- Литература по cross-view: модели, обученные на одном ракурсе, «часто отказывают» на незнакомых; рабочие приёмы —
  геометрическая нормализация скелета/координат относительно опорного объекта (что уже сделано) и отказ от абсолютных
  пикселей. Калибровка уверенности под сдвигом домена ненадёжна («модель не знает, чего не знает»), поэтому
  полагаться надо на **проверки доказательств** (якоря найдены / не найдены), а не на softmax-порог.
- **Снять 2–3 своих ролика** телефоном с нового ракурса (любая комната, стол, «дверь», кружка) и прогнать: это дешёвый
  сдвиг домена, ловит падения на этапе якорей. Результат вставить в питч как «проверено на ракурсе вне датасета».
Источники: https://arxiv.org/pdf/2508.17025 (cross-view online action detection), https://arxiv.org/pdf/1607.06408 (MCAD),
https://arxiv.org/html/2601.00138v1 (abstention под сдвигом домена), https://arxiv.org/pdf/2208.12084

### 7. Описания без выдуманных утверждений как инженерная гарантия — защищает 15 нормативной базы и репутацию
**Ожидаемый прирост:** 2–4 балла + снятие риска «−всё» при явной галлюцинации перед банковским жюри.
- Описание собирается шаблоном из полей события (тип, время, измеренные величины, какие кадры), VLM (если включена)
  даёт только флаги да/нет, не текст. Каждое предложение описания должно иметь «источник» — поле детектора.
- Отдельные слова-маркеры для вывода («предположительно», «по виду») и запрет на слова, которых детектор не измеряет
  («пересчёт», «купюры», «клиент предъявил документ»), если нет соответствующего признака.
- Для `no_violation` — тоже короткое описание (доп. поле), что проверено: «посетителей: 2, кассир на месте 98 % времени,
  дверь закрывалась в течение 4 с» — жюри видит, что «норма» — результат проверки, а не отсутствия модели.
Источники: https://arxiv.org/pdf/2607.24348 (DeepFaith), https://arxiv.org/html/2604.23366v1 (GSAR: typed grounding)

### 8. Продукт для «второй линии»: таймлайн, кадры, подтвердить/отклонить, журнал аудита, экспорт — 10 баллов
**Ожидаемый прирост:** 4–7 баллов. Банковские жюри (по обзорам XAI в банках и критериям «Цифрового прорыва»: UI,
практическая применимость, полнота требований) оценивают именно сценарий работы контролёра.
- Один сценарий от начала до конца: загрузил → ждёт (прогресс) → список событий с кадрами и нормой → контролёр
  подтверждает/отклоняет с комментарием → **журнал аудита** (кто, когда, что изменил, версия модели, уверенность) →
  экспорт отчёта (PDF/Excel). Audit trail с версией модели и переопределением человеком — то, что перечисляют
  как минимум для AI в банке.
- Показать экономику ложных тревог: «на 40 видео — 0 ложных; при 200 касс × 8 ч норма — N проверок в день для
  контролёра». Жюри-банк считает нагрузку на людей, не AUC.
- Пакетная загрузка (несколько видео) — одна из причин потери балла у команды Альфа-Банка на «Цифровом прорыве».

### 9. Техническая гигиена: один командой, лицензии, модели-карты, воспроизводимость — 10 баллов
**Ожидаемый прирост:** 3–6 баллов. На «Цифровом прорыве» команда получила 1 балл из 3 за «запускаемость» из-за
отсутствия описания файлов в репозитории — при хорошей модели.
- `README`: запуск одной командой (docker compose / `make run`), требования к железу (M3 Pro 18 ГБ), таблица моделей с
  лицензиями (уже есть в `ml_model.md` — вынести в `LICENSES.md`), явное «облачных AI-API нет, распознавания лиц нет».
- `scripts/evaluate.py` с воспроизводимыми метриками leave-one-cabinet-out, фиксированные версии зависимостей, smoke-тест
  API (`tests/test_api_contract.py`) — то, что жюри может запустить само.
- Логи времени на видео (budget / cheap-mode) — доказательство выполнения лимита 5 мин.

### 10. Питч: честные ограничения + дорожная карта + запасное видео демо — доступ к шортлисту
**Ожидаемый прирост:** косвенный (шортлист), но в «Продукт» и «Техника» это до 3–5 баллов за ясность.
- Победители технических треков: один доведённый подход, честный рассказ о недоделках, «ход мыслей»; наказывается
  «распыление» и цифры без источника (разделять измеренное и ожидаемое).
- Записать видео демо (2 прогона), иметь скриншоты; при сбое — переключиться без отладки на сцене.
Источники: https://habr.com/ru/companies/alfa/articles/876086/ , https://hacktribe.co/blog/how-to-build-a-hackathon-pitch-deck-practical-5-minute-structure ,
https://angelhack.com/blog/hackathon-tips-for-winners/

### Что НЕ делать (отрицательный ожидаемый прирост)
- Включать VLM-2B как детектор новых типов (на тесте: +FP, 0 новых TP, +20–34 с на вопрос).
- Аугментация видео (ухудшила cabinet-CV 0.725 → 0.65).
- «Подстраховочные» события с низкой уверенностью ради локализации — в per-event метриках это FP, в per-video — шум,
  который жюри прочитает как галлюцинацию.
- Любая LLM-генерация описаний свободным текстом.

## (b) Питч на 5 минут для банковского жюри

Принцип: 60 % времени — на критерии с наибольшим весом (детекция/локализация/нормы), демо — одна сквозная история,
измеренные цифры отделены от обещаний. 6–7 слайдов.

| Время | Слайд | Содержание | Сообщение жюри |
|---|---|---|---|
| 0:00–0:30 | 1. Проблема | Кассовый узел: уход от места с незаблокированным ПК, деньги без присмотра, посторонний в зоне, открытый сейф. Сегодня — выборочный просмотр архива человеком. Цена пропуска: недостача/операционный риск; цена ложной тревоги: время контролёра. | Мы понимаем *их* риск-карту, не абстрактное «CV» |

## (c) Чек-лист перед сдачей

### C1. Контракт API (обнуляет 55 баллов)
- [ ] `POST /api/v1/analyze`, multipart, поле `file`; ответ `{"job_id": "...", "status": "processing"}` (код 200/202).
- [ ] `GET /api/v1/jobs/{job_id}` → `processing | done | failed`; `queued` наружу не отдаётся.
- [ ] Неверный/отсутствующий `X-API-Key` → 401 JSON; неизвестный `job_id` → 404 JSON (не HTML, не 500).
- [ ] `Content-Type: application/json; charset=utf-8` на всех ответах; никакого HTML-редиректа (например, `http→https`,
      trailing slash `/analyze/`).
- [ ] Поля результата: `verdict` ∈ {`violation`, `no_violation`}; `violations: []` при норме (не `null`);
      `type`, `timecode_sec` (число), `description` (строка UTF-8), `evidence_frames[]{timestamp_sec, image_base64}`.
- [ ] `image_base64` — чистый base64 JPEG **без `data:image/jpeg;base64,`**; 1–3 кадра; размер кадра ≤ ~200 КБ.
- [ ] `type` совпадает с перечнем ТЗ посимвольно; нет `NaN/Infinity`; `timestamp_sec ≤ длительности видео`.
- [ ] Доп. поля (`confidence`, `rule`, `scene_checks`) не ломают схему; `demo` поле удалено из прод-ответа.
- [ ] `DEMO_MODE=false`, `ANALYZER_COMMAND` указывает на прод-анализатор; проверено запросом с «чужого» хоста.

### C2. Время и нагрузка (таймаут 5 мин от загрузки)
- [ ] 6 видео (включая 145-секундное) загружены **одновременно** → все `done` < 5 мин от момента загрузки каждого.
- [ ] Загрузка сохраняется на диск сразу, mtime не меняется; при нехватке бюджета — `cheap`-режим, результат `done`,
      а не `failed`.
- [ ] Холодный старт: первый запрос после перезапуска сервера (загрузка моделей +8 с) укладывается в бюджет;
      модели прогреты при старте сервиса.
- [ ] Память: N параллельных воркеров × пик RSS < 18 ГБ на M3 Pro; swap не используется.
- [ ] Ноутбук не засыпает, нет блокировки экрана/сети; питание от сети; процесс под supervisor с автоперезапуском.
- [ ] Хост доступен извне (туннель/HTTPS-сертификат валиден, не self-signed без договорённости), ключ передан жюри.

### C3. Входные данные
- [ ] `.mov` H.264 **и HEVC** (ffmpeg декодирует), 464×848 портрет и ландшафт, 25/30/60 fps, переменный fps, без аудио.
- [ ] Имена файлов с кириллицей/пробелами; файл ≥ 100 МБ; повторная загрузка того же файла → новый `job_id`.
- [ ] Повреждённый/пустой файл → `failed` с JSON-ошибкой, сервис не падает.

### C4. Качество выдачи
- [ ] Главное событие первым; ≤ 3 событий; нет дублей одного типа ближе 10 с.
- [ ] Таймкод — онсет по конвенции разметки (момент у двери / первый кадр действия), смещение per type вычтено.
- [ ] Кадры: `t−3`, `t`, `t+5…10` с; на кадрах видно то, что написано в описании.
- [ ] Описание: «Наблюдается / Квалификация / Норма», только измеренные факты, пункт НПА сверен с `normative_sources.md`.
- [ ] Для `no_violation` — краткий отчёт проверок (доп. поле).
- [ ] Прогон всех 40 видео через **API** (не через скрипт) — результаты совпадают с `evaluate.py`; детерминизм при повторе.
- [ ] Своя съёмка с нового ракурса: нет ложного срабатывания; `scene_checks` корректно отражают, что найдено.

### C5. Репозиторий и питч
- [ ] README: запуск одной командой, железо, переменные окружения, таблица моделей и лицензий, «нет облака / нет лиц».
- [ ] `tests/test_api_contract.py` проходит против запущенного сервиса; smoke-скрипт `curl` из ТЗ в README.
- [ ] Версия модели/коммит в ответе API и в журнале аудита; теги на коммите, который сдаётся.
- [ ] Запасное видео демо (2 прогона) + скриншоты; таймер репетиции ≤ 4:30; распределены ответы на Q&A.

### Типовые причины «нуля» в автооценках (сводка)
| Причина | Эффект | Защита |
|---|---|---|
| Другой путь/поле (`/api/jobs`, `video`) | 0 по всем видео | алиасы + контрактный тест |
| Статус `queued` или иной enum | парсер жюри ждёт вечно | маппинг наружу |
| `data:` префикс / PNG / огромный base64 | кадр не декодируется, ответ медленный | валидатор ответа |
| 1 воркер, 5 загрузок подряд | таймаут хвоста очереди | N воркеров / бюджет / частичный `done` |
| `DEMO_MODE=true` | выдуманные события на всех видео | удалить из прод-сборки |
| HEVC `.mov` не декодируется | `failed` на части видео | ffmpeg с HEVC, тест |
| Сон ноутбука / сертификат | сервис недоступен | supervisor, проверка извне |
| `null` вместо `[]`, `NaN`, HTML-ошибка | ломается парсер | строгая сериализация + тесты |
