CashGuard — о решении

Datathon 26 · кейс ForteBank · контроль кассовой дисциплины по видео. Результат — подсказка для проверки человеком, не юридическое заключение.

1. Адреса

Интерфейс: https://fortecashguard.up.railway.app

API (ТЗ §10): POST https://fortecashguard.up.railway.app/api/v1/analyze (поле file) → job_id; GET https://fortecashguard.up.railway.app/api/v1/jobs/{job_id} → processing | done | failed и результат. Ключ — в заголовке X-API-Key, без ключа — HTTP 401.

curl -X POST https://fortecashguard.up.railway.app/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video.mov"
curl https://fortecashguard.up.railway.app/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"

2. Запуск и использование

  • Интерфейс: загрузить .mov → статус обработки → вердикт «Нарушение не обнаружено» / «Обнаружены признаки возможных нарушений», события с таймкодом, 1–3 кадра-доказательства, описание и норма.
  • Один контейнер: React-интерфейс, Go API, Python-анализатор; Postgres для истории. Сборка: docker build . (корневой Dockerfile) или docker compose up -d --build.
  • Все веса загружаются при сборке образа; для анализа интернет не нужен (HF_HUB_OFFLINE=1) — переносится во внутренний контур банка.
  • Лимит 5 минут считается сервером от момента загрузки; при одновременной загрузке нескольких видео время делится между ними, ответ приходит всегда.

3. Архитектура и модели

  • Восприятие (всё локально, CPU): YOLOX-M/S (Apache-2.0) — люди и предметы; RTMPose-m (Apache-2.0) — поза; CLIP ViT-B/32 (MIT) — смысловые пробы; OWLv2-base (Apache-2.0) — предметы на столе и ключ в замке. Опционально Qwen3-VL (Apache-2.0) на Mac.
  • Сцена без координат камеры: трекинг людей, выбор кассира и его рабочего места, зоны стола/двери/сейфа выводятся из движения людей; все расстояния — в долях роста кассира. Распознавания лиц нет.
  • Решение: кандидаты событий → по одному измеренному признаку и обученному порогу на тип (11 включённых правил); отбор признаков по перекрёстной проверке «исключи камеру целиком» (7 постановок); функция потерь 2·пропуск + ложное.
  • Описание события строится только из измеренного: «Наблюдается / Квалификация / Норма + дословная цитата».
  • Качество на 40 видео датасета: проверка «новая камера» (каждая из 7 постановок исключалась из обучения) — 0,775 верных вердиктов, 0 ложных тревог на 19 нормальных видео; все 40 видео на этом стенде — 35/40, 0 ложных; тип верен у 15 из 16 найденных; медиана ошибки таймкода 0,6 с (оценка на данных разработки).

4. Нормативные источники и сопоставление

Только акты РК, тексты сверены с adilet.zan.kz: постановление Правления НБРК от 29.11.2019 № 231 (Правила кассовых операций и инкассации) — основной; постановление НБРК от 24.02.2020 № 14; постановление АРРФР от 03.04.2026 № 53. Каждый тип связан с документом, пунктом и дословной цитатой. Если норма не описывает наблюдаемое действие прямо, она помечена «связанное требование». Сервис не утверждает того, что по видео проверить нельзя (проводки, сверки, блокировки учётной записи).

6. Ограничения и известные ошибки

  • Не распознаются действия рук с деньгами: приём без документа, возврат денег клиенту, вскрытие сумки без пересчёта, вложение отбракованных купюр.
  • Типы с 1–2 обучающими примерами (сейф, ключ, напиток, экран) имеют пороги без статистической опоры: на новом ракурсе возможен пропуск. Модель настроена не выдавать ложных тревог.
  • Экран считается по ноутбуку; отдельный монитор может не распознаваться как рабочая станция.
  • Посторонний распознаётся только при коротком пребывании стоя (< 12 с) или при трёх и более людях; долгое присутствие стоящего человека может быть пропущено.
  • На общем CPU облака длинные видео анализируются с пониженной частотой кадров; если она ниже 1 кадра/с, результат помечается предупреждением.
  • Если рабочее место кассира не найдено (необычный ракурс), результат выдаётся с предупреждением «вывод ненадёжен».
